# Review: request-changes

Reviewed the faxd daemon (server/faxd/*.py, web/index.html, install.sh, faxd.service) against docs/faxd-spec.md at commit 2a8cd7a. Caveat first: another process was rewriting this repository during the first half of the review — HEAD moved 0408289 → 6378b4d → 92aa1d8/0ed0e82 → 2a8cd7a and the tree was dirty (all of server/ modified) for a stretch. Every finding below was re-read from `git show 2a8cd7a:<path>` and its line numbers checked against the now-clean working tree; anything committed after 2a8cd7a is out of scope. The job state machine and the four reconciliation areas named in the request are coherent and well tested: rules 2 and 4 correctly refuse to touch finished rows, `_apply` now routes every transition through `set_state_if` so a stale observer copy cannot regress `sending` (and test_19/test_20 pin that), filename re-drops get fresh rows, and the queue-meta identity rebuild is sound. I found no auth bypass (auth is checked before routing, `?token=` is confined to `GET /events`, and responses are HTTP/1.0 so an unread body cannot desync a keep-alive connection) and no lock cycle (every path takes AmiProgress._lock before the DB RLock, and poll_sessions issues its AMI action outside the lock). The three things I want fixed are narrower: a SELFTEST receipt can never settle once outqueue/SELFTEST.env is gone (job stuck in `dialing` forever, receipt re-parsed every scan); the AMI reader has no liveness detection at all, so a wedged-but-open session leaves `connected()` permanently true and the watchdog blind; and Last-Event-ID replay is unbounded while `job_events` is never pruned, which on this 1 vCPU / 805 MB box turns a routine browser reconnect into hundreds of lock-held queries plus a fetch stampede. I did not run the suite (read-only mandate), so all claims come from reading code.

### [medium] server/faxd/spool.py - A SELFTEST receipt can never settle once outqueue/SELFTEST.env is gone: the job stays `dialing` forever and the receipt is re-parsed on every scan

`_receipt` short-circuits the self-test branch before the generic fallbacks: `row = self._selftest_row(path); if row is None: return False` (spool.py:291-294). `_selftest_row` (spool.py:325-334) starts with `os.stat(env_path)` on `outqueue/SELFTEST.env` and does `except OSError: return None`, so if SELFTEST.env is gone the receipt is *never* applied — and because `_receipt` returned False, `_rule_receipts` never records it in `self._receipts_done` (spool.py:278-279: `if self._receipt(...): self._receipts_done[path] = sig`). Consequences: (1) the self-test job, whose only terminal source of truth is `sent/SELFTEST.txt` (the docs record that the pipeline writes no `<jobid>.txt` for it), is stuck in `dialing` permanently — `/status` reports `queue.dialing: 1` forever and the page shows a fax that never finishes; (2) `sent/SELFTEST.txt` is stat'ed, parsed and looked up on every 2 s scan for the life of the install. The branch also skips `_receipt_candidates` and `_adopt_receipt`, so with a rebuilt registry (documented as supported: "history is rebuilt from the share") past self-tests are never adopted. Test gap: test_11/12/13 (test_spool.py:283-314) all `_write` SELFTEST.env first, so "receipt with no SELFTEST.env" is untested. Live evidence covers only the benign case — docs/handoff.md:38 says the self-test completed in 24 s, i.e. SELFTEST.env was still there; the failure needs faxd down/restarted (or the DB deleted) across a self-test, or pbx_spool consuming the .env before the receipt lands.

**Fix:** Fall through instead of returning: if `_selftest_row()` yields nothing, continue into the existing `_receipt_candidates` path (SELFTEST.txt sits in `sent/` beside the moved `<filename>.pdf`, and `To: SELFTEST` won't contradict the row's number), and only then give up. Either way remember the attempt so it is not re-read forever — e.g. a `_receipts_skipped` set keyed by sig, so a genuinely newer SELFTEST.txt still gets another chance.

### [medium] server/faxd/ami.py - AMI reader has no liveness detection: a silent peer or a wedged Asterisk leaves `connected()` true forever and the watchdog blind

`_fill` (ami.py:187-196) only calls `recv` after `select.select([sock], [], [], 0.5)` reports readability, looping `while not self._stop.is_set()`. `sock.settimeout(5.0)` (ami.py:137) is therefore never in force: a connection that goes quiet without FIN/RST makes `_read_packet` → `_read_until` → `_fill` spin forever. Nothing notices: `_session` only returns (and `_run` only reconnects) when `_read_packet` yields None, `SO_KEEPALIVE` is never set anywhere in the tree (grep: no matches), and there is no periodic Ping or read-idle deadline. `alive()` (ami.py:95-98) reports the *thread*, which is still running, so `Daemon.dead_threads()` (main.py:118-122) stays empty and `check_once` never returns 3. `connected()` stays true, so `/status` lies. Concrete path: Asterisk is SIGSTOPped or its manager thread wedges, or ami_host is ever pointed beyond loopback (the config allows it, and design.md's whole premise is VPN) — faxd goes permanently deaf, jobs stall in `dialing` until a disk receipt rescues them. Compounding: `registrations()` catches the resulting AmiTimeout and returns `value = []` (main.py:44-51) while `ami_connected` is true, and index.html only shows "PBX link down" when `daemon.ami_connected === false`, so the pill reads "daemon ok".

**Fix:** Give the reader an idle deadline instead of an infinite select: track `last_rx` in `_fill` and treat ~120 s of silence as a dead session (send `Action: Ping` after ~30 s idle, reconnect if the pong is missing). Cheapest correct version: `SO_KEEPALIVE` plus TCP_KEEPIDLE/KEEPINTVL/KEEPCNT, and a blocking `recv` whose `socket.timeout` counts as a miss.

### [medium] server/faxd/api.py - Last-Event-ID replay is unbounded while `job_events` is never pruned: one reconnect can mean hundreds of queries and thousands of browser fetches

`_replay` pages `job_events_since(after, limit=REPLAY_PAGE)` in a `while True` until a short page (api.py:431-437), then issues one `reg.get_job(job_id)` per distinct job (api.py:439-442), all before the 200 goes out (api.py:463). Each call takes the single Registry RLock (db.py:131), so the spool thread and every HTTP handler queue behind it. Nothing ever deletes from `job_events` (grep for DELETE FROM/VACUUM/prune/retention in server/faxd: no matches), and a row is appended for every transition *and* every non-state annotation — `set_state_if` inserts unconditionally (db.py:189-191), which `_annotate` calls with the state unchanged for pages/detail (ami.py:322-328), re-triggered every 2 s by `poll_sessions`. So the table grows monotonically and replay cost grows with it. The trigger is ordinary: index.html uses EventSource, which resends `Last-Event-ID` on every reconnect, so a laptop that slept over the weekend replays everything since. Each replayed `job` event fires `on("job", () => { loadJobs(); loadInbox(); })` (index.html:204) — two fetches per event, uncoalesced — against a server capped at 32 connections (api.py:20) that is still busy running the replay.

**Fix:** Bound the replay the way uploads are bounded: cap the paging loop and the emitted event count, and fall back to the `updated_since` catch-up the spec already defines. Cheap structural fix: replace the per-job `get_job` loop with one `WHERE id IN (...)` query in pages, costing a handful of lock acquisitions instead of thousands. Add retention too (periodic `DELETE FROM job_events WHERE ts < now - N days`), since today the only way to shrink it is deleting the DB — which the spec notes resets SSE event ids.

### [low] server/faxd/web/index.html - The merged `receiving`/`from` flags are never cleared, so "Receiving a fax from …" stays on screen indefinitely

`setStatus` accumulates: `s = lastStatus = Object.assign({}, lastStatus, s)` then `if (s.receiving) say("Receiving a fax" + (s.from ? " from " + s.from : "") + "...")` (index.html:170-171). ami.py's `_receiving` publishes only the partial `{"receiving": true, "from": …}` (ami.py:386-388) and a full `/status` payload never contains a `receiving` key (main.py:55-63), so nothing writes `receiving: false` back into `lastStatus`. After the first inbound fax the flag is true for the life of the page: every later status event and every `start()` re-displays "Receiving a fax from <old number>..." even when the receiver is disarmed, and it overwrites `act()`'s feedback ("Queued.", "Armed.") because both write to `#msg`. The spec mandates the merge (docs/faxd-spec.md, web/index.html) but no code path clears the key.

**Fix:** Treat `receiving` as a self-expiring flag rather than a merged boolean (record `lastReceiving = Date.now()` on a partial event, show the banner only while it is under ~120 s old), or have `status_fn()` include `receiving: false` in the full payload so the merge resets it — which preserves the spec's "merge, never replace" rule.

### [low] server/faxd/api.py - Idempotency-Key is global, not scoped to the caller: a reused key suppresses a different client's fax and returns that other job

`_prior` is `self.api.reg.find_by_client_key(key) if key else None` (api.py:337-339) and `find_by_client_key` is `SELECT * FROM jobs WHERE client_key=?` with no client/direction predicate (db.py:218-223), backed by a plain `CREATE UNIQUE INDEX jobs_client_key` (db.py:60). `r_post_job` and `r_test_send` answer 200 with whatever row that returns (api.py:343-346, api.py:397-399), and in the POST /jobs case `_discard_body()` drops the PDF — so a second client whose key equals an earlier one gets someone else's job back and its fax is never queued. All users share one bearer token (config.py `token`, printed once by install.sh), so this is a naming-collision hazard rather than an access-control break: docs/client-spec.md:79 prescribes `Idempotency-Key: <guid>` but nothing server-side enforces it, and the tests use short keys like `"t.1"` (test_api.py:504). The returned row also discloses another send's `to_number`, `subject` and `client`.

**Fix:** Scope the key to its creator: `find_by_client_key(key, client)` → `WHERE client_key=? AND client=?`, and make the migration index `UNIQUE(client, client_key)`; or namespace server-side as `<client ip>|<key>`. If global keys are intended, at least answer 409 rather than silently returning a different job when the stored row's `to_number` differs.

### [low] server/faxd/spool.py - `FAXD_POLL_INTERVAL` is used unclamped, so 0 or negative turns the poll loop into a busy loop

`run` ends with `stop.wait(self.cfg.poll_interval)` (spool.py:465-469) with no floor, and `config.load` only guards `ValueError`, falling back to the default (config.py:130-141). `FAXD_POLL_INTERVAL=0` parses cleanly, `Event.wait(0)` returns immediately, and `scan_once` then runs back-to-back — eight rules, several `_listdir`s and a `list_jobs` per unsettled receipt — on a 1 vCPU box whose design premise is "Poll, do not busy-loop" (docs/faxd-spec.md, Constraints). A NaN value also parses and would raise out of `wait`, killing the spool thread → `check_once` returns 3 → a restart loop bounded only by StartLimitBurst.

**Fix:** Clamp where it is consumed: `interval = max(0.2, cfg.poll_interval)` in `SpoolObserver.run`, and reject non-finite values in `config.load` alongside the existing ValueError path.

### [low] server/faxd/main.py - `registrations()` holds a process-wide lock across a 5 s AMI round trip, serialising every /status and /events connect

The cache check and the AMI call are both inside `with lock:` (main.py:39-52), and `ami.action` defaults to `timeout=5.0` (ami.py:232). `status()` calls `registrations()` on every `GET /status` (api.py:264-266) and on every SSE connect (api.py:462), so while one request waits on Asterisk, all other handlers block behind it; with a wedged session (see the AMI liveness finding) each new arrival waits the full 5 s in turn. Against `MAX_CONNS = 32` (api.py:20) and a browser that reconnects EventSource every few seconds, handler threads and connection slots are consumed by waiting, which looks like a hung daemon while every watchdog thread is demonstrably alive.

**Fix:** Serve stale and refresh off the critical path: read the cache under `lock`, then do the `ami.action` outside it (or guard the refresher with `lock.acquire(blocking=False)`), returning the previous value to callers while a refresh is in flight.

### [low] server/faxd/enqueue.py - An enqueue interrupted between the .part write and os.replace leaves a `queued` row and a dotfile that nothing ever reaps

`enqueue_pdf` writes `outbox/.<name>.part` (enqueue.py:94-99), the row, then `os.replace(part, final)` (enqueue.py:109); the failure path unlinks and marks the row failed only if the `except` runs (enqueue.py:110-120). If the process is killed instead — plausible with `MemoryMax=96M` (faxd.service) against two concurrent 25 MB upload buffers (`MAX_BODY`/`MAX_UPLOADS`, api.py:19-21) — the dotfile stays in outbox and the row stays `queued`. No rule can move it: `_rule_outbox` skips names beginning with "." (spool.py:193), and nothing reaps by age anywhere. The job then shows as queued in `/status` and the table forever, and `queue-meta/<name>.json` keeps its identity so a later rebuild would adopt the phantom id.

**Fix:** Add a reap step to the existing scan (the observer must stay read-only per spool.py's docstring, so fix the state rather than delete files): rows in `queued` whose `pdf_path` does not exist and whose `updated_at` is minutes old get `set_state_if(id, ("queued",), "failed", error="file never appeared")`.

### [low] server/faxd/db.py - `converting` is a state nothing ever produces, so `queue.converting` is permanently 0

`converting` is in `JOB_STATES` (db.py:15) and appears only on the consuming side: `_ACTIVE` tuples (ami.py:11, spool.py:29), `set_state_if(row["id"], ("queued", "converting"), "dialing")` (ami.py:333), the rule-2 guard (spool.py:246) and `QUEUE_STATES` (main.py:30). No line of server code writes state="converting" (grep across server/faxd returns only those read sites), and the only conversion signal on disk is the failure marker `failed/convert-failed-<filename>` (spool.py:372). So a job sits in `queued` through the whole ghostscript PDF→TIFF pass — the phase most likely to take seconds on this box — and `queue.converting` can never be non-zero. test_status_counts_converting (test_main.py:202) asserts only the counter using a hand-inserted row, so the gap is invisible to the suite. design.md's chain (`queued -> converting -> dialing -> sending(page n/m)`) is partly aspirational.

**Fix:** Either produce it — rules 1/2 can set `converting` when the outbox file exists but no `<jobid>.env` has appeared and `sending/<name>` is absent, which is precisely the conversion window — or drop `converting` from `JOB_STATES`/`QUEUE_STATES` and record in the spec that phase 1 cannot observe it.

### [low] server/install.sh - The AMI secret file is created with the shell's umask before the chmod, so it is briefly world-readable on a fresh install

Step 4 writes the secret with a here-doc redirect, `cat > "$AMI_CONF" <<EOF` (install.sh:120-128), and only afterwards applies `chown root:asterisk` / `chmod 0640` (install.sh:128-129). On a first install `$AMI_CONF` does not exist, so `cat >` creates it with the umask-derived mode (0644 for root's default umask), leaving a window in which any local user can read `secret = …`. On a re-install the file is truncated in place and keeps 0640, so the exposure is install-time only. The rest of the script is careful about exactly this (`mktemp` for the sudoers fragment, `install -m 0640` for settings.env). The spec states only the end state: "must be readable by the `asterisk` user (`chown root:asterisk`, mode 0640)".

**Fix:** Create it with the right mode atomically: write to a `mktemp` and `install -m 0640 -o root -g asterisk "$tmp" "$AMI_CONF"`, or `umask 077` before the here-doc and chmod after.

The growth claim in finding 3 comes from counting how many job_events rows one job produces (transitions plus per-annotation writes), and the OOM path in finding 9 from `MemoryMax=96M` versus two 25 MB upload buffers.

If that read is denied, `_listdir` swallows the OSError (spool.py:87-90) and every job would stall in queued/dialing with no error anywhere; I could not check which is true live.
