# Review: comment

Reviewed eeb92ef (LAN Fax printer moved from a file port to the named-pipe port \\.\pipe\LANFax) against its parent c677f1a and the pre-attempt state 0ced417. The core work is solid: the pipe listener's lifecycle (first-instance creation, spare instance, stop grace, stale-part sweep), the EofCounter state machine, the measured DACL (NETWORK deny, Authenticated Users 0x13019b), the tracker-based duplicate-send protection, and the installer migration all check out, and the tests exercise real named pipes, real PowerShell 5.1, and a live stock printer rather than mocks. The headline problem is in session-end handling: WM_ENDSESSION stops the listener only while IsReceiving is true, but IsReceiving lags the spec's own "from the moment a client is connected" definition by an async hop, leaving a narrow inter-job window in which a forced sign-out/shutdown can silently lose a small job the spooler has already fully written into the pipe buffer. Remaining findings are low-severity observability, doc, and test-strength gaps; nothing blocking was found. I did not run the test suite, the elevated scripts, or a real sign-out (read-only run), which is noted in could_not_verify.

### [medium] client/LANFax.App/Logic/SessionEnd.cs - WM_ENDSESSION only stops the listener while IsReceiving, so a job already connected to the spare in the inter-job gap can be lost silently on a forced session end

OnEndSession returns without stopping the listener unless receiving() is true at the exact moment WM_ENDSESSION arrives (line 16: 'if (!ending || !receiving()) return false;'). IsReceiving is set in PrintPipeListener.ServeAsync only after ConnectedAsync returns (SetReceiving(true) after the await; SetReceiving(false) in the finally after the previous job's file is saved). The spooler starts the next job on the spare instance as soon as the previous connection is closed, so between the previous job's conn.DisposeAsync() and the next SetReceiving(true) the next job can already be connected and written into the kernel pipe buffer while IsReceiving is false. The spec (client-spec.md, 'In flight') defines IsReceiving as 'true from the moment a client is connected', which the code does not meet in that gap. If the session ends in that window (WM_QUERYENDSESSION was answered FALSE, but the user/system can still force it), the listener is never stopped, Windows kills the process, and a job the spooler has already fully written (a small PDF fits the ~4 KB default pipe buffer; the test FiftyTinyJobsThatCloseBeforeTheListenerWaitsAllArrive demonstrates such jobs arriving complete before the listener reads them) is lost with no trace: the spooler's write succeeded, so the job leaves no 'Error' state in the queue and the next start's stuck-jobs check has nothing to announce. Larger jobs fail the spooler's blocked write and remain in Error (announced at next start), so the silent-loss case is the fully-written small PDF, but that is the exact failure this product exists to prevent. The fix is cheap: stop the listener unconditionally when ending (drop the receiving() condition). When idle, Stop returns almost immediately (the loop is parked in WaitForConnectionAsync and exits on cancellation), and ServeAsync's stopping path already reads a client that is already connected on the spare within StopGrace (covered by StopReceivesTheNextJobThatAlreadyConnectedToTheSpare), so the residual window shrinks to near zero.

**Fix:** In SessionEnd.OnEndSession, call stopListener() whenever ending is true, not only when receiving() is true; log the distinction instead of skipping the stop. The ReceivingChanged-based ShutdownBlockReason still governs WM_QUERYENDSESSION; only the ENDSESSION safety net changes.

### [low] client/LANFax.App/TrayContext.cs - Stuck-jobs queue check runs exactly once, 60 s after listener start; jobs that enter Error later are not announced until the next start

AnnounceStuckPrintJobsAsync (line 498: 'await Task.Delay(StuckCheckDelay);') lists the queue a single time, 60 s after the listener starts, and only reports jobs 'submitted before the start and still in Error'. The measured no-listener retry lasts 4+ minutes (docs/handoff.md, client-spec.md 'Why a pipe port'). A job printed shortly before start that is still being retried at the 60 s mark (status not yet Error) is therefore never announced in that session when the spooler gives up minutes later; it sits in 'Error, Printing' in the queue until the next app start, when the one-shot check catches it. The 30 s PrinterCheck timer only reads the printer's registry port, never the queue. This is documented behavior (the docstring says 'still in Error 60 s later'), but it is an observability gap for the primary stuck-job scenario the feature exists for.

**Fix:** Re-run the PrintQueueJobs.StuckSince check on the existing 30 s _printerCheck timer (or a few additional times over the first ~5 minutes) until the first Error-state job is announced, keeping the one-balloon-per-job behavior via a small seen-set.

### [low] docs/client-spec.md - Spec's rate-limiting sentence is inaccurate for the 'cannot open an instance' case

Line 197: 'Rate limiting: pipe-level failures (cannot open an instance, cannot save) raise Error at most once per distinct reason per 60 s'. In PrintPipeListener, the name-taken 'cannot open' case is reported from Start (rateLimited: false) and then re-reported from RunAsync's retry loop only every NameTakenRepeat (10 minutes), again with rateLimited: false — not the 60 s window; and a spare-instance creation failure (ServeAsync, 'no spare instance') is Log-only and never raises Error at all. Only 'cannot save a print job' and the idle-disconnect report actually use the 60 s rate limit.

**Fix:** Reword the bullet: name-taken is reported once at start and repeated every NameTakenRepeat (10 min); 'cannot save' and the sent-nothing report are rate-limited once per 60 s; spare-instance creation failure is logged only.

### [low] client/LANFax.App/Logic/PrinterSetup.cs - Installer migration handed over while the tray is running leaves the rescued print.pdf unoffered until the next start

TrayContext scans spool\jobs exactly once, before _spool.Start() in the constructor ('Before the watcher starts, so a fresh print job is never mistaken for an unsent leftover'). InstallPrinterAsync (tray menu 'Install/Fix printer') runs the elevated script, whose migration moves a non-empty leftover spool\print.pdf that passes Test-SinglePdf to spool\jobs\<guid>.pdf. When the tray is already running (the normal way the user fixes the printer, since the Misconfigured balloon's click opens this path), that file lands in jobs\ but is not offered: there is no re-scan after the install, so the document waits until the next start. No data is lost (the file stays in jobs\ and Scan offers it as New next time), but the 'leftover print.pdf offered' behavior promised by the commit message only applies when the tray was not running. Related migration-time edge: a job spooled before the port switch that finishes rendering after the hand-off can recreate spool\print.pdf, which nothing reads any more.

**Fix:** After InstallPrinterAsync succeeds, re-run _tracker.Scan() and EnqueueSend the new offers (deduped by SpoolId), or at least log that a rescued document was moved to jobs\ and will be offered at next start.

### [note] client/LANFax.Tests/PrintQueueJobsTests.cs - The only live test of the hand-rolled JOB_INFO_1 marshalling asserts nothing about the fields the stuck-jobs feature depends on

AnInstalledPrinterCanBeListed (line 34 comment: 'Exercises OpenPrinter/EnumJobs and the JOB_INFO_1 layout on a queue every Windows 10/11 has') asserts only 'j.Id > 0 && j.SubmittedUtc.Kind == DateTimeKind.Utc'. PrintQueueJobs.StuckSince depends on the JobInfo1 struct's Status DWORD and Submitted SYSTEMTIME being read from the correct offsets, and docs/handoff.md admits 'The balloon itself is not exercised live yet (needs a job in Error on the real printer)'. A wrong offset or a misnamed field (e.g., Document vs UserName) would pass this test: garbage Submitted collapses to DateTime.MinValue via the caught ArgumentOutOfRangeException and still has Kind == Utc, and a misread Status simply never matches JobStatusError. (I cross-checked the layout against the superseded commit c677f1a's SpoolerKeptJobs, which used the identical 6-pointer/5-DWORD struct and whose live -Crash probe runs recorded in the handoff required correct multi-job listing, deletion by id, and real page-count values — so the layout is believed correct, but the test provides no guard for it.)

**Fix:** In AnInstalledPrinterCanBeListed, submit a one-page job to the stock printer, wait for it to reach a known status, and assert that PrintQueueJobs.List reports a SubmittedUtc within a sane window of the submission time (and, when the job is in Error, that the error flag is set); compare against Get-PrintJob as an independent reference.

### [note] client/LANFax.Core/PrintPipeListener.cs - A program that creates the pipe while the listener is serving joins it undetected (mid-run squatter variant)

Name-taken detection fires only when the listener creates a first instance (Start and RunAsync's re-take after 'every instance is gone'). If another local program creates \\.\pipe\LANFax while the listener is already serving, the listener's next CreateInstance(first: false) for the spare (ServeAsync, after each job) succeeds by joining that existing pipe, and the kernel dispatches the spooler's connections across all instances — so jobs can be delivered to the squatter while IsListening stays true and no Error is raised. This is the same threat class as the design-accepted 'another local process can take the pipe name first' case (detected, not prevented), but this variant is not even detected. A full fix requires the out-of-scope SYSTEM service noted in the handoff.

**Fix:** At least document the variant in the CreateSecurity/RunAsync docs and in the spec's first-instance paragraph; optionally treat a spare-creation success when no first instance is known to exist as suspicious and report it once.
