### [low] client/LANFax.App/Logic/ClientRuntime.cs:327 - Cancel-boundary hole in the live-token guard: a resync/status event dispatched by a cancelled run is lost, while its job/received twin is kept even across a server change

EventStream advances LastEventId before dispatching (EventStream.cs ReadAsync: `if (id != null) LastEventId = id; if (hasData) Dispatch(...)`). Between `oldCts?.Cancel()` on the owner thread (RestartStream, L364) and the old run noticing cancellation, the run can still dispatch events. Status/arm/resync go through PostLive (L311-335) and are dropped — for status/arm that is safe (faxd re-sends full status and arm at every stream open, api.py `_sse("status"...); _sse("arm"...)`), but a `resync` dropped this way is never replayed by the new run (the stream already counted its id) and never re-raised, so the grids keep the gap until some later trigger. Conversely, `job`/`received` go through the unguarded `Post` (L348-356) and are applied unconditionally — the doc comment justifies this with LastEventId, which holds only for a same-server restart: after a settings save to another server (TrayContext.OpenSettings L389-390 calls `_monitor?.ServerChanged()` then `SettingsSaved()`), an old-server event still in the owner queue lands in the just-cleared MonitorModel and the new server's loads never remove it (merging keeps rows the answer omits). ClientRuntimeTests covers the drop of a late *status* event ('A_cancelled_runs_late_events_are_dropped...') but not either side of this boundary for resync/job events.

**Fix:** When PostLive drops a resync, fall back to a guarded reload (e.g. remember `resyncPending` and have the next connect reload from the earliest pending since); on the job/received path, stamp each event with the run token and skip ApplyJobUpdate/InboxChanged when the run was cancelled by a *settings save that changed the endpoint* (or simply have ServerChanged bump a model generation that ApplyJobUpdate respects).

### [low] client/LANFax.App/TrayContext.cs:93 - Stale comments: second start now shows the monitor window, but Program.cs/InstanceGuard.cs still say the running tray shows its "already running" balloon

TrayContext.cs:93 registers `(_, _) => OnUi(ShowMonitor)` and docs/client-spec.md was updated ('signals the running tray to show its monitor window (as "Open LANFax")'), but Program.cs:15 still reads 'the running tray was asked to show its "already running" balloon', and Logic/InstanceGuard.cs:7 (InstanceRole.Running doc) says the same. The balloon no longer exists anywhere in the new code (old c9c7781 TrayContext had `OnUi(() => Balloon("LANFax is already running"))`).

**Fix:** Update the two comments to describe the show-window signal.

### [low] client/LANFax.App/TrayContext.cs:148 - Second start during the 30 s exit wait gives the user no feedback at all

ShowMonitor returns immediately on `_exiting || _exitPending` (L148). During ExitAppAsync's 'wait for the send in flight' phase `_exitPending` is set for up to ExitWait (30 s), so a second launch that signals the show event produces neither a window nor a balloon — the old code always ballooned 'LANFax is already running' regardless of exit state (c9c7781 TrayContext registered wait callback). The second process itself says nothing in the same-session role (Program.cs returns silently). docs/handoff.md lists the show path as 'Untested wiring' but not this silent window.

**Fix:** Fall back to a balloon (or `_tray.Visible` flash) when the show signal arrives while `_exitPending`; keeping `_exiting` silent is fine.

### [low] client/LANFax.App/MainForm.cs:211 - Arm card can keep the previous server's ARMED countdown after a settings save when the status snapshot was already Empty

ArmCallAsync sets `_arm` straight from the HTTP answer (L211), independent of the runtime snapshot. On a settings save, ResetStatus (ClientRuntime.cs:392-399) early-returns when `Status` is already `ServerStatus.Empty`, raising no StatusChanged — so if the stream was not connected at save time (typical right after pointing at a new, briefly unreachable server while an arm HTTP call had answered), the form keeps rendering 'ARMED (mm:ss left)' for the old server's window until the new stream delivers an arm/status event. docs/handoff.md logs 'arm state in three places' as debt; this is the user-visible corner of it. MonitorModel.ArmDetail itself checks out (floor seconds, h:mm:ss ≥ 1 h, '(ending)' past the end).

**Fix:** Have MainForm.ServerChanged() reset `_arm` to disarmed (or route button answers through a planned `ClientRuntime.NoteArm`, the phase-4 item), so a server change always clears the card.

### [low] client/LANFax.App/Logic/MonitorModel.cs:189 - PdfCachePath accepts Windows reserved device names, so a server-supplied id like "nul" fails PDF opening with a raw file error

SafeId (`^[A-Za-z0-9_-]{1,64}$`, L196) plus the directory check correctly stop every traversal case the tests try ('..', 'C:\\x', 'con:' — MonitorModelTests A_hostile_id_never_leaves_the_cache_dir), but a bare reserved name ('nul', 'aux', 'com1') passes both: `GetFullPath(cacheDir\\nul.pdf)` stays inside the dir. FaxApi.DownloadPdfAsync then fails creating `nul.pdf.part` (a plain IOException from the FileStream in CopyBodyAsync, FaxApi.cs ~L166), which PdfOpener reports as 'Could not open the PDF: ...'. No data can escape the cache dir — the doc's claim is about path containment and holds — but the id is server-supplied and the failure is silent-by-design noise rather than a clean rejection.

**Fix:** Extend the id check to reject names whose first dot-segment is a reserved device name (CON, PRN, AUX, NUL, COM1-9, LPT1-9), and add the case to the hostile-id theory.

### [low] client/LANFax.App/Logic/MonitorLoader.cs:68 - Two failed passes report the load failure twice (confirmed handoff leftover)

When a pass fails and a coalesced pass was queued, the loop runs the second pass (L73-77 comment: 'A request that arrived meanwhile ... still runs, even after a failure'); if that also fails, `failed(e)` fires again, so MainForm.Say shows two error lines and FileLog gets both. MonitorLoaderTests covers fail-then-succeed (A_failed_load_still_runs_its_queued_follow_up_once...) but not fail-then-fail. Already logged in docs/handoff.md 'Monitor leftovers'; confirming it stands in the current code (generation check L71 only suppresses cross-server failures).

**Fix:** Track whether `failed` was already called for this ReloadAsync invocation (reset at entry) and call it once; fold into the planned move into ClientRuntime.

### [note] client/LANFax.App/Logic/ClientRuntime.cs:289 - The "left behind" stream run survives into Dispose's HttpClient disposal after StopAsync timed out

StopAsync waits the run at most StreamStopWait and logs 'still ending after the stop; left behind' (L262-266). If that path is taken, ExitAppAsync proceeds to ExitThread and Program's `using var runtime` then runs Dispose — which, because `_stopped` is already true, skips the wait (L279-287) and disposes `_http`/`_sseHttp` (L289-291) while the abandoned run may still be mid-read on `_sseHttp`. The Dispose doc promises the opposite ('so the stream run ends before its HttpClient goes') for the StopAsync path; it only holds when StopAsync was *not* called first. Consequence is limited: the run catches everything (`catch (Exception e) { Error("event stream ended", e); }`, L381), raises nothing (Post/PostLive check `_stopped`), and the process is exiting — one logged ObjectDisposedException.

**Fix:** Either re-wait `Task.WhenAny(_sseTask, ...)` in Dispose when a run was left behind, or amend the doc comment to state the exception case.
