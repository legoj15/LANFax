# Review: comment

Reviewed server/faxd (12 modules, web page) against docs/faxd-spec.md and the tests in server/tests/. Headline: no blocking defect. The one-shared-sqlite-connection design in db.py is correctly locked (every connection use is under the RLock, close() is race-free), no token-less request can read a PDF or create a job (query token restricted to GET /events, hmac.compare_digest, fullmatch routes, internal-only pdf_path), reconciliation covers the SELFTEST double-env and filename-reuse cases, and every thread/socket/queue/dict is bounded. I found six low-to-medium issues, the most substantive being that AmiClient.db_get can never complete against real Asterisk because its test fake fabricates a DBGetComplete event the real protocol does not send, and that SpoolObserver._apply can briefly regress a sending job to dialing in a narrow race with the AMI thread. Confidence is high for the in-repo claims; the Asterisk DBGet wire-format claim is based on Asterisk's implementation, not verifiable from this repo.

### [medium] server/faxd/ami.py - db_get can never complete against real Asterisk: DBGet listing is never closed

ami.py:216 marks a successful DBGet response as the start of a listing (`more = ... or p.name == "DBGet"`), and ami.py:223 only ends listings on `EventList: complete` or an event name ending in "Complete". Real Asterisk DBGet replies `Response: Success` ("Result will follow") followed by a single `Event: DBGet` packet with Family/Key/Val and no EventList Start/Complete framing — unlike true list actions. So for any existing key the pending listing is never finished and `action("DBGet")` (ami.py:250) blocks the full 5 s timeout and raises AmiTimeout, violating the spec's `db_get(...) -> str | None` contract; the not-found path (Response: Error) completes fine, which is why the failure only appears for present keys. The repo's fake masks it: test_ami.py:16 fabricates `{"Event": "DBGetComplete", "EventList": "Complete"}`. db_get/db_put/db_del/get_var are only exercised by tests, not by phase-1 daemon code, so this is latent until a later phase uses the AMI database.

**Fix:** In _route, treat the `Event: DBGet` packet itself as the terminator of the DBGet listing (append it, then `del self._pending[aid]; p.finish()`) instead of waiting for a Complete marker; update the fake in test_ami.py to the real single-packet protocol so the test would have caught this.

### [low] server/faxd/spool.py - SpoolObserver._apply can regress a job's state (sending -> dialing) racing the AMI thread

spool.py:151 applies state changes with the unconditional `self.reg.set_state(...)` using the row dict fetched earlier under a separate lock acquisition (e.g. spool.py:195 in _rule_env). The spec documents `set_state_if` as the guard that keeps state from moving backward ("so a `sent` row never moves back") and AMI uses it (ami.py), but the spool side does not. Concrete window: _rule_env leaves a row `queued` with `ast_jobid` set when `<jobid>.result` already exists at first sighting (the condition encoded by test_2b, spool test 'test_2b_env_with_result_does_not_dial'); the AMI thread can then process VarSet (queued->dialing via set_state_if) and FAXStatus (dialing->sending) between the observer's fetch (line 195) and its `set_state(id, "dialing")` (line 151), regressing a transmitting job to `dialing` and publishing a spurious `job` event. Impact is bounded: the next FAXStatus re-enters `sending` (dialing is in _ACTIVE) and the receipt still wins the terminal state, so it self-heals.

**Fix:** In _apply, replace `set_state` with `set_state_if` using the appropriate precondition (e.g. expected_states=("queued","converting") for the dialing transitions in _rule_env/_rule_sending, and the active states for receipt/marker applications), and treat a None return as "already moved forward" — the same pattern AmiProgress uses.

### [low] server/faxd/main.py - Daemon.stop() closes the shared registry while HTTP request threads may still be running

main.py:125-131: stop() sets the stop event, stops AMI, calls api.shutdown(), joins the three worker threads, then `self.reg.close()`. But api.py:425-429 only stops the serve_forever loop and closes the listener; the thread-per-request handlers are daemon threads (api.py `_Server.daemon_threads = True`) and are never joined. An in-flight request thread (a slow /jobs/<id>/pdf stream, a /status call in an AMI round-trip, or an SSE thread in its 0.5 s tick) can be mid-Registry-call when close() runs: `_conn()` (db.py:85-88) then raises sqlite3.ProgrammingError("registry is closed"), which _handle turns into a 500, and in r_events (api.py:348) an SSE thread can die with an uncaught traceback after it already sent the 200 event-stream headers.

**Fix:** Either keep the Registry open until process exit (move reg.close() to a finalizer / drop it, since the process exits right after main() returns), or have Api.shutdown() wait for in-flight request threads to drain (track live handler threads, or set block_on_close=True) before the caller closes the registry.

### [low] server/faxd/arm.py - Hung fax-arm.sh surfaces as 500 instead of the spec's 502 with the script's message

arm.py:69 runs `self.runner(argv, capture_output=True, text=True, timeout=20)`. If fax-arm.sh hangs past 20 s, subprocess.run raises subprocess.TimeoutExpired, which is not an ArmError. api.py's _handle maps only ArmError to 502 ("a failing arm script (ArmError) is 502 with the script's message" per spec); TimeoutExpired falls into the generic handler and returns 500 {"error": "internal error"}, losing the timeout information and misclassifying an arm-script failure as a daemon bug.

**Fix:** In ArmController._run, catch subprocess.TimeoutExpired and raise ArmError("arm script timed out after 20s") (and consider catching subprocess.SubprocessError generally) so the API returns 502 with a meaningful message.

### [low] server/faxd/spool.py - to_number stored as empty string (not null) for outbox names without digits before the first underscore

spool.py:178-182: for a name without an underscore, `base = os.path.splitext(name)[0]` and `to_number: _norm(base)`. `_norm` never raises and returns `re.sub(r"\D", "", s)` (spool.py:38-43), so a file like `nonum.pdf` (created by test_spool.py 'test_missing_dirs_and_malformed_files_tolerated') produces `to_number=""`, which is stored as an empty string rather than NULL and returned as such by /jobs and the SSE job events. The spec defines to_number as the digits before the first `_`; a name with no digits has no number, so the row should carry null (the env rule's `to_number=to or None` at spool.py:214 already normalizes empty to None, so this only affects rows that never see their .env).

**Fix:** Use `"to_number": _norm(base) or None` in _rule_outbox.

### [low] server/faxd/api.py - Exception in status_fn() after SSE headers corrupts the event stream instead of closing it

api.py:359: in r_events, `self._sse("status", api.status_fn())` runs after send_response(200) + end_headers(). If status_fn raises a non-OSError (e.g. sqlite3.ProgrammingError when the registry is being closed during shutdown — see the main.py finding — or any future bug in build_status_fn), the exception escapes the `except OSError` at api.py:368, reaches _handle, and _safe_json(500, ...) calls send_response again, writing a second HTTP status line and a JSON body into the middle of an already-started text/event-stream. The client's EventSource sees garbage and reconnects; the unsubscribe in finally still runs, so it is not a leak, but the stream is corrupted and the failure is logged as an unhandled 500 instead of a clean client disconnect.

**Fix:** Wrap the initial status/arm sends (and the status_fn()/arm.state() calls) in a try/except that, on failure, just returns (the finally already unsubscribes), or compute the initial payload before sending the 200 headers.

## Could not verify

- Did not run the test suite or the daemon: this is a read-only run and executing python would write bytecode/temp files and bind sockets, so all conclusions are from reading the code, not from observed test outcomes (the handoff log claims 139 tests passing on 0.1.1).
- Real Asterisk 20.6 DBGet wire format (basis of the ami.py medium finding): the repo's fake AMI server (server/tests/fake_ami.py:14-17) encodes a DBGetComplete/EventList protocol that I could not verify against the live server; the claim that Asterisk's DBGet sends a single Event: DBGet packet without EventList framing comes from my knowledge of Asterisk's manager implementation, and the faxserver box is not reachable from this environment.
- Bash-pipeline retry semantics (server-side, not in this repo): whether pbx_spool can write failed/<jobid>.txt and later sent/<jobid>.txt for the same JOBID on retry. If it can, spool.py:266 (`if row["state"] in ("sent", "failed") and row["state"] != target: return True`) would leave the later success ignored and the job stuck as failed. The spec's terminal-row rule sanctions skipping changed receipts on finished rows, so this is unresolvable without the pipeline scripts on the server.
- install.sh, deploy.ps1, and faxd.service were not reviewed: outside the requested scope (Python daemon + tests), so spec compliance of the installer (swap, sudoers, manager.d, ufw) is unverified.
