# Review: request-changes

Spot-checked the two most recent commits (6bb8c02, 7b94dc1) in client/ against the five failure classes (wrong number, double send, lost document, token loss/leak, startup crash), reading all changed sources plus the server API they contract with. The send path is otherwise sound: the number mirror matches faxd's normalize/check exactly, the idempotency ordering on the server (auth 401 before key lookup, key lookup before body validation, 409 on number mismatch) validates the client's Rejected/Uncertain classification, the persisted record is written before the first byte, and no new startup crash path was found. The headline problem is a hole in the new "frozen send endpoint" feature: a send resumed from disk is not pinned to the server its key was sent to, so a Settings server change plus a restart can replay the key to a different faxd and dial twice. A second medium issue is that tokens are saved untrimmed/unvalidated, and a whitespace token makes every send fail as a false "uncertain" lock plus unhandled exceptions in the poll loop. Four low findings (token-migration corner case, catch-up limit, Load misclassification, elevation quoting) round out the report. I did not execute the build/tests, and the spooler's back-to-back FILE-port behaviour is explicitly an unrun probe in the spec, so those are listed as unverified.

### [medium] client/LANFax.App/Logic/SendSession.cs - Send resumed from disk is not pinned to its server; server change can replay the key and dial twice

The frozen-endpoint guard only works in-session. TrackedJob (client/LANFax.App/Logic/JobTracker.cs:27) persists the IdempotencyKey and plan but no endpoint; SendSession.Resume (line 98, private ctor at line 87) leaves LockedServer null, and the guard in SendExecutor.RunAsync (client/LANFax.App/Logic/SendExecutor.cs:58) is 'if (session.LockedServer is { } pinned)' — it never fires for a resumed session. Scenario: an attempt to faxd A times out (record written 'uncertain', key K — JobTracker.BeginSend/RecordFailure); the user changes the server in Settings (e.g. faxd moves to a new host) and saves; the app restarts; TrayContext's constructor auto-opens 'unsent documents', the dialog shows ResumeNote (SendSession.cs:70) claiming 'Send will not create a duplicate'; the user clicks Send. The same key K goes to faxd B, whose database has no K (find_by_client_key in server/faxd/db.py:281 is per-instance), so B creates a new job and dials — a second fax if A had already dialed. The new in-session guard is tested (SendExecutorTests 'A_locked_send_is_not_resent_to_a_different_server'), but the on-disk resume it was meant to protect is not covered. This defeats the stated invariant in JobTracker's doc comment that a crash 'never turns into a duplicate fax'.

**Fix:** Persist the endpoint base URI in TrackedJob (write it in BeginSend/RecordFailure from the SendEndpoint snapshot) and set LockedServer from it in SendSession.Resume, so the existing mismatch check at SendExecutor.cs:58 also applies to resumed sends (or at minimum show the 'may already be queued on X' warning when the stored server differs from Settings).

### [medium] client/LANFax.App/SettingsDialog.cs - Token is saved untrimmed and unvalidated; a whitespace token locks every send as false 'uncertain' and throws in the poll loop

Candidate() (line 97) stores '_token.Text' verbatim — the host is trimmed ('_host.Text.Trim()') but the token is not, and ClientConfig.Load/Save and Validate() never touch it. A token containing whitespace or non-ASCII (easy when pasting or typing) makes 'new AuthenticationHeaderValue("Bearer", ep.Token)' at client/LANFax.Core/FaxApi.cs:306 throw FormatException. In the send path that throw happens in make() before the network try in FaxApi.SendAsync, escapes PostWithRetryAsync (which only catches FaxApiException), and SendOutcome.Classify (client/LANFax.App/Logic/SendSession.cs:35-38) maps a non-API exception to AttemptOutcome.Uncertain — so the dialog locks the fields with 'The server may already have this job' and JobTracker.RecordFailure writes an 'uncertain' record, even though provably nothing was sent. In TrayContext.PollTrackedAsync/CatchUpInboundAsync, which only catch FaxApiException/JsonException, the same throw surfaces on the UI thread via Application.ThreadException on every 60 s tick; the event stream degrades to 401 (token is URL-escaped there). The state is recoverable (Cancel keeps the document; fix the token and resend with the same key), but it is a misleading lock plus unhandled-exception churn from a common input mistake.

**Fix:** Trim the token in SettingsDialog.Candidate() (and defensively in ClientConfig.Load/Save), and/or reject a token that is not a valid Bearer parameter with FaxApiConfigException in SendEndpoint.From/Req so the send path classifies it as NotSent with a clear message instead of Uncertain.

### [low] client/LANFax.Core/ClientConfig.cs - Token migration deletes the shared machine-scope token even when the user's own token.bin fails to decrypt

LoadToken sets 'bool userFile = userBlob != null' (line 131) — file existence, not successful decryption — and the removal gate at line 153 is 'if (userFile && m is { Token.Length: > 0 })'. If the user's %LocalAppData% token.bin exists but is undecryptable (blob copied from another machine, e.g. profile move, or corrupt), Token stays null with a LoadError, yet the still-decryptable machine-scope token in the shared config.json is nulled and rewritten away — the only on-disk copy of the token is deleted and the user must re-enter it (the server still holds it, so it is re-obtainable). The symmetric case is handled: an undecryptable shared token 'return[s]' without touching the shared file (line 148 comment 'leave the shared file alone: nothing was moved'), but the user-file-failure path is not gated on a usable token.

**Fix:** Gate the shared-token removal on a usable token in memory ('Token != null') instead of 'userFile', so an undecryptable user blob leaves the shared token in place for retry.

### [low] client/LANFax.App/TrayContext.cs - Inbound catch-up with limit=100 silently never announces older faxes when >100 arrived while disconnected

CatchUpInboundAsync (line 333) fetches 'GET /jobs?direction=in&state=received&limit=100&updated_since=<LastSeen>' once; the server's list_jobs orders by 'ORDER BY created_at DESC, rowid DESC LIMIT ?' (server/faxd/db.py:332), so the 100 returned are the newest by creation. If more than 100 received faxes qualify, the older ones are neither fetched nor marked in InboundAnnouncer, and Absorb advances LastSeen to the newest updated_at fetched — so the next catch-up's updated_since filter (inclusive 'updated_at>=?' on the server) moves past them and they are never announced. The faxes themselves remain in the server inbox (no document loss), but the 'Fax received' balloon the catch-up exists to deliver is missed for a busy line with a long disconnect.

**Fix:** Paginate the catch-up: loop while a full batch (100 rows) is returned, advancing the cursor to the oldest created_at/updated_at in the batch (or fetch with a higher limit, up to the server's 1000 cap).

### [low] client/LANFax.App/Logic/JobTracker.cs - Record that vanished between enumeration and read is classified 'Unavailable (in use)' and its PDF is not offered until the next start

Load() maps 'FileNotFoundException or DirectoryNotFoundException' to LoadStatus.Unavailable (line 308) — a branch documented as 'held open by another process (antivirus, backup)' — and Scan() treats Unavailable records as 'skipped this scan' (lines 146-152), which also suppresses the PDF offer in the second loop ('if (skipped.Contains(id)) continue;'). If a <guid>.json is deleted out-of-band (user, sync/backup tool) while its PDF remains, the document is silently not offered at this startup and waits for the next one. The outcome is conservative (no duplicate risk), but the classification is wrong for a genuinely absent record.

**Fix:** Return a distinct 'missing' status for FileNotFound/DirectoryNotFoundException from Load and let Scan offer the orphan PDF as SendKind.New (the existing no-record path), instead of adding it to 'skipped'.

### [low] client/LANFax.App/Logic/PrinterSetup.cs - Elevated PowerShell argument lines do not escape double quotes in -SpoolDir/-PrinterName

BuildArguments (line 89) embeds '"{printerName}"' with no escaping, and the self-elevation relaunch in client/install/Install-LANFaxPrinter.ps1:20 and Uninstall-LANFaxPrinter.ps1:20 embeds $SpoolDir/$PrinterName into $argLine the same way. printerName and spoolDir come from config.json, which any local user can write (the installer grants BUILTIN\Users Modify on the data dir by design). A value containing a double quote shifts parameter binding in the elevated 'powershell.exe -File ...' invocation. The impact is bounded — everything after '-File <script>' is bound as script parameters, not executed as commands, so this is quoting confusion in the new PS 5.1 elevation path rather than code execution — but it is an unescaped interpolation into an elevated command line.

**Fix:** Validate/escape the values before building the argument string in the app (reject printer names with quotes), and in both scripts escape '"' (or switch to single-quoted values with '' doubling) when composing $argLine.

## Could not verify

- Windows spooler FILE-port behaviour for back-to-back jobs (overwrite vs append vs fail while print.pdf is still present) — docs/client-spec.md marks the elevated probe as 'Result still pending'. If the port overwrites, a job spooled while the app is not running and the previous file is still on the port path is lost before the new %%EOF guard can act; nothing in the code can defend against that case, so I could not assess it from code alone.
- That 'new AuthenticationHeaderValue("Bearer", <token with whitespace/non-ASCII>)' throws FormatException on the target .NET 10 runtime — I am confident from the constructor's documented token/quoted-string validation, but this run was read-only and I did not execute any code.
- Test-suite and build results (dotnet test / build.ps1 were not run; the .NET 10 SDK was not invoked in this read-only review). In-repo tests assert the behaviours I relied on for intent (e.g. LocalMachine-scope blob decryptable without the LocalMachine flag in ConfigHardeningTests), but I did not run them.
- Behaviour on real Windows machines for DPAPI per-user blobs (cross-machine undecryptability) and for the Global\ mutex DACL case in Program.TryOwnMachineMutex — inferred from the code and MSDN semantics only.
