# Review: request-changes

Reviewed the C# client (LANFax.Core, LANFax.App, both test projects, Inno installer, printer scripts) against docs/client-spec.md and docs/faxd-spec.md. The core fax-safety invariants hold up: I found no path for a fax to go to the wrong number, out twice, or out without confirmation (validation, idempotency-key persistence-before-first-byte, key rotation only on definite 4xx, resume locking, suspect confirmation all match the spec). However, I found five concrete defects: the SSE `resync` contract is unimplemented with no `updated_since` catch-up anywhere in app code, the Inno uninstaller silently deletes %ProgramData%\LANFax (token, unsent faxes, sent copies) contradicting the uninstall script's documented intent, the spec-mandated back-to-back-print spooler probe was never recorded and its append contingency (%%EOF detection) was never implemented, the self-elevation relaunch in both printer scripts pre-quotes arguments in a way that breaks on Windows PowerShell 5.1 at the installed path, and restarting the event stream on settings save resets Last-Event-ID. Confidence is high on the first four (all grounded in code and spec text I read); I could not execute tests, the spooler probe, or a real uninstall to observe runtime behavior.

### [medium] client/LANFax.Core/EventStream.cs - SSE `resync` event is unhandled and no `GET /jobs?updated_since=` catch-up exists anywhere in the app

docs/faxd-spec.md ('Event ids and replay') states: 'At most 200 missed job_events rows are replayed: with more, the server sends a single event: resync, id = the newest event overall, data {"reason": "too_many_events", "since": "<ts of the oldest missed row>"}, and no job events; the client reloads with GET /jobs?updated_since=<since>.' In EventStream.Dispatch (switch at line 120) only 'job', 'received', 'arm' and 'status' are handled — 'resync' falls through the switch and is dropped silently (not even logged). Worse, the resync event's id: line updates LastEventId (line 93: `if (id != null) LastEventId = id;`), so the client will never replay the missed events. I verified by grep that nothing in the app ever calls FaxApi.GetJobsAsync with updatedSince — only LANFax.Tests/FaxApiTests.cs does. Failure scenario: the stream is down long enough that >200 job_events are missed on reconnect; the server sends resync; the client loses all of it. In the current app the concrete loss is the 'Fax received from …' balloon (TrayContext only learns about jobs via es.JobChanged/es.Received plus the 60 s poll, and the poll in TrayContext.PollTrackedAsync covers only _tracker.Pending and _submitted).

**Fix:** Add a `case "resync"` in Dispatch that parses `since` from the data and raises a new `Resync(string since)` event; in TrayContext subscribe to it and call `_api.GetJobsAsync(updatedSince: since)` feeding each row through OnJobChanged (this is also the reconnect grid-reload the client-spec Monitor section requires for the phase-3 MainForm).

### [medium] client/install/LANFax.iss - Uninstall silently deletes %ProgramData%\LANFax (token, unsent faxes, sent copies) — contradicts the uninstall script's 'Leaves the spool folder'

The [Dirs] entries at lines 35-37 (Name: "{commonappdata}\LANFax", "…\spool", "…\spool\jobs", each with Permissions: users-modify) carry no `noremove` flag. Inno Setup's documented default is that [Dirs] directories — including their contents — are deleted by the uninstaller unless `Flags: noremove` is set (the noremove flag's own description says 'the contents are also not deleted', i.e. they are by default). So uninstalling removes config.json (the DPAPI-protected server token), every unsent document and its send record in spool\jobs, and every keep-local-copies PDF in spool\sent — none of which the user was warned about. This directly contradicts the companion script: Uninstall-LANFaxPrinter.ps1's SYNOPSIS says 'Removes the LAN Fax printer and its file port. … Leaves the spool folder.', and the script itself only removes the printer and port.

**Fix:** Add `Flags: noremove` to the three [Dirs] entries (or at least to spool and spool\jobs), or — if data deletion on uninstall is the intended behavior — say so in the README and drop the 'Leaves the spool folder' claim.

### [medium] client/LANFax.Core/SpoolWatcher.cs - Back-to-back print jobs: the spec-mandated spooler probe was never recorded and its 'appends' contingency (%%EOF detection) was never implemented

docs/client-spec.md ('Spool path and the printer') requires: 'Phase-2 probe (do first, record the result here): print two jobs back to back … record whether the second overwrites, appends, or fails while the first is still present. … if it appends, the app must detect %%EOF count and split, or reject and notify.' I read the whole spec: no probe result is recorded. And SpoolWatcher validates only the 4-byte %PDF header (lines 120-125) before `File.Move(PrintPath, dest)` at line 143 — there is no %%EOF counting, splitting, or rejecting anywhere in the file. Failure scenario: if the spooler appends a second job's PDF to print.pdf before the first is moved (the stability window is ~1.5 s: MinAge 1 s + SizeRecheck 500 ms), the concatenated file starts with %PDF, passes the check, and is offered as a single fax — the user's fax goes out as a corrupted/merged document. If the spooler instead truncates the existing file in place for job 2, job 1's data is destroyed and the spooler will not retry (from its view the job was delivered), so the first fax is silently lost. The 'fails' contingency is covered by the spooler's own retry, but the other two outcomes are unguarded.

**Fix:** Run the phase-2 probe and record its result in client-spec.md as the section instructs; if append is possible, implement the spec'd contingency — reject (Error + keep or delete) files whose %%EOF count is not exactly one, or split them — and consider an in-place-truncation guard (e.g. verify the file still contains the bytes that were header-checked before moving).

### [medium] client/install/Install-LANFaxPrinter.ps1 - Self-elevation relaunch pre-quotes ArgumentList entries; on Windows PowerShell 5.1 an installed path containing a space is split into two arguments

Lines 19-22 build `$argList` with already-quoted entries — `('"{0}"' -f $PSCommandPath)`, `('"{0}"' -f $DataDir)`, etc. — and pass them to `Start-Process -ArgumentList`. Windows PowerShell 5.1 (the default `powershell.exe`, and the very interpreter the Inno script invokes via `{sys}\WindowsPowerShell\v1.0\powershell.exe`) joins ArgumentList into a single command line, wrapping entries that contain spaces in quotes again; an entry that is already quoted becomes `""C:\Program Files\LANFax\install\Install-LANFaxPrinter.ps1""`, which native argument parsing splits into `C:\Program` and `Files\…`. The installed location is `{autopf}\LANFax\install` (LANFax.iss line 21: `DefaultDirName={autopf}\{#AppName}`) — it contains a space. The self-elevation branch is a designed path: client-spec.md notes 'The dev shell is not elevated. Printer install/uninstall must run elevated.', so a user running the installed script from a non-admin shell hits it. The tray-menu and installer paths are unaffected (they launch the script already elevated, so the branch is skipped). PowerShell 7's Start-Process passes ArgumentList natively (no re-quoting), so the same code works there — the behavior is version-dependent and I could not execute it to confirm on a 5.1 box. Uninstall-LANFaxPrinter.ps1 lines 17-19 have the same pattern.

**Fix:** Pass the paths unquoted in ArgumentList (let Start-Process add the single pair of quotes, which is correct on both 5.1 and 7), or set `ProcessStartInfo.ArgumentList` directly on a started process instead of pre-quoting.

### [low] client/LANFax.App/TrayContext.cs - StartEventStream creates a fresh EventStream on every settings save, resetting LastEventId and dropping replay

StartEventStream (line 177) is called from the TrayContext constructor and again from OpenSettings after a successful save; each call constructs `new EventStream(_cfg, _sseHttp)` (line 191). The new instance's LastEventId starts null, so the reconnect after a settings save sends no Last-Event-ID header and the server sends no replay (faxd-spec: replay is driven by Last-Event-ID / ?last_event_id). Any job that transitions in the gap between the old stream's cancellation and the new stream's connect is missed: a 'Fax received from …' balloon is lost permanently (no catch-up path exists — see the resync finding), and tracked jobs only self-heal on the next 60 s poll. Note the fresh instance buys nothing: EventStream builds its URL and reads cfg per connect (EventStream.cs: `new Uri(cfg.BaseUri, "events?token=" …)` inside StartAsync), and TrayContext passes the shared _cfg instance, which SettingsDialog.Save mutates in place — so a single long-lived EventStream would pick up the new token/server on its next connect while retaining LastEventId.

**Fix:** Keep one EventStream instance for the app's lifetime (subscribe once); on settings save, cancel its CTS and re-run StartAsync with a new CTS instead of constructing a new EventStream.
