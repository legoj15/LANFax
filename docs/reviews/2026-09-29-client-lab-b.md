# Review: request-changes

Deep read of client/LANFax.Core, client/LANFax.App (+ tests), client/install and the two specs, cross-checked against server/faxd/api.py and enqueue.py. The idempotency design is genuinely careful — journal-before-first-byte (SendDialog.cs:216), key freeze on uncertain / rotation on 4xx (SendSession.cs), one dialog per spool id (TrayContext.cs:292), spool move atomicity — and the DPAPI P/Invoke is correct (16-byte DATA_BLOB layout on x64, LocalFree on pbData, UiForbidden|LocalMachine on protect only). The defects I found are concentrated in failure *classification* and wiring rather than in the state machine: a config value that cannot form a URI is mis-reported as "the server may already have this job" and strands the document; a resumed record that gets a definite 4xx can never be sent or edited; and the same Idempotency-Key can be replayed against a different server if Settings are saved during a retry backoff, which is the only real duplicate-phone-call path I could construct. Confidence: high for the Core/App findings (each re-read after the tree changed mid-review); the Inno [UninstallRun] timing and the runtime validity of {commonappdata} could not be verified here.

### [high] client/LANFax.Core/FaxApi.cs:236 - A malformed Server/Port is classified as an uncertain send, falsely locking the dialog and journaling a key that was never used

ClientConfig.Load accepts any int for Port (`if (m.Port is int p) c.Port = p;`, ClientConfig.cs:68) and any non-blank string for Server (:67), and nothing checks that `BaseUri` (`new UriBuilder(Uri.UriSchemeHttp, Server, Port).Uri`, ClientConfig.cs:19) is constructible. BaseUri is evaluated lazily *inside* the request factory: `new Uri(cfg.BaseUri, path)` at FaxApi.cs:236, called from `using var req = make();` at FaxApi.cs:251 — which sits in SendAsync's try whose only filter is `when (IsNetwork(e, ct))` (HttpRequestException/TaskCanceled/Timeout, FaxApi.cs:245). So a UriFormatException/InvalidOperationException from the UriBuilder->Uri conversion escapes FaxApi unconverted. In SendDialog the attempt has already been handed to the session (`Session.Started(plan)`, SendDialog.cs:225), so `Session.Failed(SendOutcome.Classify(failure))` (:244) maps any non-FaxApiException to Uncertain (SendSession.cs:31-32) → LockedPlan is set, ApplyLock() makes the number/subject read-only with 'The server may already have this job' (:251), and JobTracker.RecordFailure writes state `uncertain` with that key (JobTracker.cs:67). Failure scenario: a user types the address as `192.0.2.10:8080` into the Server box (SettingsDialog.cs:145 only rejects whitespace) and saves, or hand-edits `"port": 0`/`70000` into config.json. Every Send then fails without a single byte leaving the process, yet the dialog says the server may already hold the fax and locks the fields; JobTracker.Scan re-offers the record as a locked Resume (JobTracker.cs:164) at every start, so the document is stranded with a wrong explanation. The same throw in StartEventStream (EventStream.cs:52) is swallowed by `catch (Exception e) { error = e; }` and turns the stream into a silent 1s→30s reconnect loop.

**Fix:** Validate on load and on save: in ClientConfig.Load require `p is >= 1 and <= 65535` and verify `c.BaseUri` round-trips (try/catch, else keep the default and set LoadError); do the same in SettingsDialog.Save before writing. Additionally, build the request URI outside the 'may be on the wire' region — or throw a dedicated pre-flight exception that SendOutcome.Classify maps to NotSent — so a failure that provably sent nothing never freezes the plan or the journal.

### [medium] client/LANFax.App/Logic/SendSession.cs:135 - A resumed record that gets a definite 4xx stays locked with the same key forever — that fax can never be sent or edited

`if (LockedPlan != null) return o;` short-circuits before the Rejected branch, and `SendSession.Resume` (SendSession.cs:87) sets LockedPlan from the stored plan, so for a resumed dialog the fields are locked from the first keystroke and a rejection neither rotates the key nor unlocks. JobTracker.RecordFailure then sees `session.LockedPlan is {} locked` and rewrites state `uncertain` with the same key (JobTracker.cs:67-73), and JobTracker.Scan:164 offers it as a locked Resume again. The dialog is a dead end: Send re-sends the identical rejected request, the number/subject are ReadOnly and the test-page box is disabled (ApplyLock, SendDialog.cs:415-421), so the user cannot fix the number or the route; Cancel takes DialogOutcome.Kept and the loop repeats next start. The lock is unnecessary here: faxd answers a repeated Idempotency-Key with 200 and the prior row *before* any body/number validation (server/faxd/api.py:342-345), so a 4xx for a key the client believes in is positive proof nothing is queued under it. Reachable chain: a document over faxd's 25 MB cap, or one whose number the client's mirror allows but the server's narrower FAXD_ALLOWED_NUMBERS rejects, that gets an uncertain record (e.g. a 30 s HttpClient timeout mid-upload on a big scan) — every resumed attempt then returns 413/400 forever. SendSessionTests.Resume_is_locked_with_the_stored_key_and_plan pins the current behaviour (`Assert.Equal("stored-key", s.IdempotencyKey)` after `Failed(AttemptOutcome.Rejected)`), so this is designed, not accidental.

**Fix:** In Failed, handle the resumed case separately: `if (Resumed && o == AttemptOutcome.Rejected) { LockedPlan = null; IdempotencyKey = _newKey().ToString(); }` before the short-circuit, so RecordFailure writes `draft` (editable, no key) and the dialog can unlock; add a matching SendDialog.RemoveLock() (re-enable _number/_subject/_testPage, hide _lockNote) called when `!Session.FieldsLocked` after a failure. Update the SendSessionTests theory row that pins the current key-retention.

### [medium] client/LANFax.App/TrayContext.cs:417 - The same Idempotency-Key can be POSTed to a different server if Settings are saved during a retry backoff (duplicate fax)

FaxApi resolves the endpoint per attempt — `new Uri(cfg.BaseUri, path)` and `r.Headers.Authorization = ... cfg.Token` at FaxApi.cs:236-237 — and TrayContext hands FaxApi the single mutable ClientConfig (`_api = new FaxApi(_cfg, _http)`, TrayContext.cs:60) that SettingsDialog.Save mutates in place (SettingsDialog.cs:142: `_cfg.Server = c.Server; _cfg.Port = c.Port; _cfg.Token = c.Token;`). OpenSettings (TrayContext.cs:417) is reachable from the tray menu while a modeless SendDialog is open (menu item wired at :73), and SendDialog also calls `_openSettings()` itself after a 401 (:255). ShowDialog runs a nested loop but does not disable the modeless dialog, and FaxApi's retry waits 2 s then 4 s inside `_busy` (PostWithRetryAsync), so the retarget window is seconds long. Failure scenario: attempt 1 times out (the server may well have queued it — that is precisely why the outcome is uncertain), the user opens Settings, points LANFax at the second fax box and saves, attempt 2 enqueues the same PDF there. faxd scopes idempotency per client_key+IP (api.py:339, `find_by_client_key(key, self.client_ip)`), so the second daemon sees a brand-new key and dials: two phone calls, two receipts, for one print job. The identical argument applies to a token change mid-retry.

**Fix:** Freeze the endpoint for the lifetime of a send: give SendPlan the absolute base Uri + token snapshot it must be sent with (or have TrayContext construct a per-dialog FaxApi from a cloned ClientConfig when the dialog opens), so retries cannot drift. At minimum refuse to open Settings, and refuse `DialogResult.OK` in Save, while `_openDialog is { Sending: true }`.

### [medium] client/install/Install-LANFaxPrinter.ps1:57 - Neither the script nor the app verifies that the printer is bound to the watched port: printing can silently do nothing

The script only calls Add-Printer when the name is absent (`if (-not (Get-Printer -Name $PrinterName ...)) { Add-Printer ... -PortName $portName }`, :57-60) and never rebinds an existing queue, while it does create `$portName` if missing (:52-56). PrinterSetup.IsInstalled only checks that `HKLM\SYSTEM\CurrentControlSet\Control\Print\Printers\<name>` exists (PrinterSetup.cs:40, via RegistryPrinterKeyReader.KeyPath) — the printer's PortName value is never read. So a queue named 'LAN Fax' that points at another port (a hand-edited SpoolDir in config.json, which ClientConfig.cs:69 accepts and JobTracker/SpoolWatcher consume directly at TrayContext.cs:61/106; an earlier install with a different path; a queue created by hand) makes the script add an orphan port, print 'printer added: False', exit 0, and have the app report 'The "LAN Fax" printer is installed.' (TrayContext.cs:406). The user prints, print.pdf is written to the old path, no dialog ever appears, and nothing logs an error. This is the exact risk the spec flags as unverified (client-spec.md: 'the silent write-to-path behaviour is unverified'). InstallScriptTests only greps the script text for Add-Printer/Add-PrinterPort, so no test covers the binding.

**Fix:** In RegistryPrinterKeyReader, also read the `PortName` value and compare it (case-insensitively) with `Path.Combine(spoolDir, "print.pdf")`; report 'installed but printing to X' when they differ and have InstallAsync pass the expected port. In the script, when the printer exists but `(Get-Printer -Name $PrinterName).PortName -ne $portName`, call `Set-Printer -Name $PrinterName -PortName $portName` instead of skipping.

### [medium] client/LANFax.App/TrayContext.cs:209 - resync only triggers a poll of tracked jobs; the parsed 'since' is unused, so missed inbound faxes are never announced

EventStream now parses the resync event (EventStream.cs:135-141) and TrayContext subscribes, but the handler just logs and calls `PollTrackedAsync()` (:209-214). PollTrackedAsync asks only about `_tracker.Pending` (pollable accepted records) plus `_submitted` (:225-232) and returns early when `_polling` is already true or `ids.Count == 0`. faxd's contract for this event is explicit: on more than REPLAY_MAX(200) missed job_events rows it sends a single `resync` with `"since": <ts of the oldest missed row>` and no replay, and 'the client reloads via GET /jobs?updated_since=' (server/faxd/api.py:432-433, docs/faxd-spec.md 'Event ids and replay'). Because the resync payload carries an `id:` line, EventStream.ReadAsync still advances LastEventId (:112), so those events are skipped permanently. Failure scenario: the laptop sleeps over a weekend with faxes arriving; on reconnect the client gets one resync, polls its own tracked outbound jobs, and never learns about any inbound fax (no 'Fax received from X' balloon — the Received handler at :216 is event-driven only). ClientConfig's `GetJobsAsync`/`GetInboxAsync` exist but have no production caller (only FaxApiTests), so nothing closes the gap.

**Fix:** On Resync, reload from the server instead of only polling: `GetJobsAsync(direction: "in", updatedSince: since ?? <last known good>)` (and the outbound list for terminal states), diffing against the ids already announced, and fall back to a windowed poll when `since` is null. Wire the same reload on a reconnect whose Last-Event-ID was rejected.

### [low] client/LANFax.Core/FaxApi.cs:112 - PostJobAsync re-buffers a byte array the caller already has: three full copies of the document per send

SendDialog reads the whole PDF (`bytes = await File.ReadAllBytesAsync(plan.PdfPath)`, SendDialog.cs:205) and wraps it in a MemoryStream (:231); PostJobAsync then copies that stream into another MemoryStream and calls ToArray() (`using var buf = new MemoryStream(); await pdf.CopyToAsync(buf, ct); var bytes = buf.ToArray();`), and `new ByteArrayContent(bytes)` adds the array retained by the retry closure across all three attempts. A 25 MB document therefore peaks at ~75 MB of LOH allocations per dialog, and there is no check against faxd's 25 MB body cap (MAX_BODY, api.py) before uploading — a much larger print job allocates until it throws, and any such throw after Started is classified Uncertain and locks the dialog.

**Fix:** Add a `PostJobAsync(byte[] pdf, ...)` overload (or send `new ByteArrayContent(bytes, 0, bytes.Length)` straight from the caller's array) and drop the copy in PostJobAsync; `plan.PdfPath`'s length should be checked against a MaxBodyBytes constant and refused as NotSent before BeginSend.

### [low] client/LANFax.App/SendDialog.cs:279 - Cancelling a 'may already have been sent' (Suspect) document deletes it, while the equivalent Resume keeps it

OnClosing maps a user close to `Session.Resumed ? DialogOutcome.Kept : DialogOutcome.Cancelled` (:280-281) and TrayContext discards the PDF+json only for Cancelled (TrayContext.cs:347-349). A Suspect request (JobTracker.cs Scan's unreadable-record / no-server-id / unknown-to-server branches, and RequestFor for MarkUnknown) is built with `LockedPlan == null`, so Resumed is false — yet its own checkbox text says 'This document may already have been sent. Sending it again may fax it a second time.' (SendSession.cs:62-63). A user who reads that and cancels rather than risk a duplicate loses the spooled document permanently, which is the opposite of the careful 'keep it' rule applied to the identical uncertainty in a resumed record (ResumeNote, SendSession.cs:60-61: 'Cancel keeps the document').

**Fix:** Return DialogOutcome.Kept when `Session.Resumed || Request.Kind is SendKind.Suspect` (i.e. whenever the record says the document may already have been sent), so the file and its json survive for the next start instead of being destroyed.

### [low] client/LANFax.App/TrayContext.cs:449 - Exit's 'wait for the send in flight' observes only the current attempt; a new attempt started during the wait is cut off by Dispose

`_exitPending` blocks new dialogs and EnqueueSend (TrayContext.cs:289, :365), but not the open dialog's Send button, and `await Task.WhenAny(dlg.Idle, Task.Delay(ExitWait))` captures the TaskCompletionSource for the attempt that was in flight when Exit was clicked (SendDialog.cs:196-205 creates a fresh _idle on every SetBusy(true)). After that task completes, the message loop keeps pumping: the user can click Send again, then `_exiting = true; ExitThread();` runs, `using var ctx` disposes (Program.cs:26) and Dispose calls `open?.Dispose()` on a form whose `await _api.PostJobAsync(...)` is still running (:472-473). The continuation then touches disposed controls from the `async void` click handler (SendDialog.cs:147). The journal record already says 'sending' with the key, so no fax is lost or duplicated, but it surfaces as an unhandled UI exception via Application.ThreadException.

**Fix:** Set `_openDialog.Enabled = false` (or `_openDialog.SetBusyLockedForExit()`) before awaiting, and wait in a loop `while (dlg.Sending && !deadline) await dlg.Idle;` so a second attempt is either honoured or impossible.

### [low] client/LANFax.App/Program.cs:14 - One machine-global spool and journal, but a session-local single-instance guard, so another user's dialog can confirm your fax

Program.cs uses `Local\LANFax.Tray` (per-session) and the installer adds an HKLM Run value (LANFax.iss [Registry]) so every interactive session starts its own tray, while the spool path and job records are machine-global (`%ProgramData%\LANFax\spool`, ClientConfig.cs:16-17) and granted `users-modify` to everyone (LANFax.iss [Dirs], Install-LANFaxPrinter.ps1:43) because the printer port is one machine-wide path. Two sessions therefore run two SpoolWatchers over the same print.pdf: the File.Move is atomic so the job is not duplicated, but whichever instance wins raises NewPrintJob and shows the number prompt on its own desktop — user A's document can be presented to user B, who may send it to a number A never confirmed; both instances also Scan and re-track the same <guid>.json records independently. FileSystemWatcher in the losing instance additionally fires a Renamed/Created storm with no visible effect.

**Fix:** Either make the guard machine-wide (`Global\LANFax.Tray` plus 'another session owns the spool' state that keeps the watcher stopped), or move the spool to a per-user path (%LOCALAPPDATA%\LANFax\spool) and install a per-user printer connection with a per-user port name.

### [low] client/LANFax.Core/Dpapi.cs:38 - Machine-scope DPAPI plus a users-modify config directory means any local user can recover (and rewrite) the fax token

Protect passes `UiForbidden | LocalMachine` (Dpapi.cs:14/38) and the blob is stored in `%ProgramData%\LANFax\config.json`, a directory the installer deliberately grants BUILTIN\Users Modify (LANFax.iss [Dirs] 'Deliberate shared-machine decision', Install-LANFaxPrinter.ps1:43 Grant-UsersModify with ContainerInherit,ObjectInherit). Machine-scope DPAPI is decryptable by any authenticated local user by design, so the spec's rule 'The app never stores the token in plain text' (client-spec.md §Build and test rules) is satisfied in form only: a standard user on a shared office PC can read the fax token (which authorizes sending faxes and reading every inbox document over HTTP) and can rewrite `server` to capture other users' jobs. The P/Invoke itself is correct (DATA_BLOB sequential layout matches x64, out-buffer freed with LocalFree, no description/entropy). Note ClientConfig.Load also drops the token silently for a *user*-scope blob, so switching scopes needs the LoadError text updated.

**Fix:** If the target machines are single-user, say so in the spec/README and keep machine scope. Otherwise store the token in the current user's own file/registry (HKCU\...\LANFax or %LOCALAPPDATA%) with user-scope DPAPI, keeping only non-secret keys (server, port, spool dir) in the shared ProgramData config.

### [note] client/LANFax.Tests/EventStreamTests.cs:49 - Test gaps that map one-to-one onto the defects above

The suites are strong on the pure logic (SendSession transition table, JobTracker journal states incl. corrupt-record and 404 paths, FaxApi retry/status shapes against a real HttpListener, the shared numbers-vectors.json parity with server/tests, SpoolWatcher stability/move/rate-limit, EventStream parse/replay/stall) — but (a) no FaxApi test exercises a Server/Port that cannot build a URI, and SendOutcomeTests only pins exceptions thrown *after* a request went out, so finding 1's pre-flight misclassification is untested; (b) resync is tested for parsing only (ResyncEventRaisesWithParsedSinceOrNull), never for what the client does with it (finding 5); (c) nothing asserts the printer's port matches the watched path — InstallScriptTests only greps the script text (finding 4); (d) SpoolWatcherTests.StopWhileAJobIsBeingProcessedLeavesItAlone covers only the pre-move cancellation check, not the move-then-stop path that writes the file back (SpoolWatcher.cs:163-169); (e) no test covers ClientConfig round-tripping a port outside 1..65335 or a host containing ':' (finding 1).

**Fix:** Add: a FaxApi test with `Server = "127.0.0.1:1"`/`Port = 0` asserting NotSent/no request; a ClientConfig test asserting LoadError + defaults for an unusable port; a TrayContext-level (or extracted-logic) test that a resync triggers a jobs/inbox reload; a PrinterSetup test that a printer whose PortName differs is reported as misconfigured; and a SpoolWatcher test that Stop after a move leaves the PDF at print.pdf (or as a scan-visible jobs\<guid>.pdf).

### [note] client/LANFax.App/Logic/NotificationText.cs:1 - Spec §Monitor (phase 3) is absent from the client, leaving Core's status/arm/inbox plumbing with no production caller

There is no MainForm.cs anywhere under client/ (verified by glob over all .cs files), and `ServerStatus.Merge`, `ArmState.RemainingMin` (outside SettingsDialog's one 'Test connection' string), `GetJobsAsync`, `GetInboxAsync`, `DownloadPdfAsync`, `EventStream.ArmChanged` and `StatusChanged` are referenced only by tests (grep across client/). So the arm card with countdown, the jobs/inbox grids, double-click-open-PDF and the 'arm window expiring in 5 min' balloon from client-spec.md §Monitor are unimplemented; 'Open LANFax' just launches the browser (TrayContext.cs:374). This matches handoff.md (phase 3 not started), but it means the receive-side half of the send/receive contract has no client surface yet.

**Fix:** No code fix needed for phase 2 if the gap is deliberate — record it in client-spec.md as phase-3 pending so the unused Core surface (and the missing arm-expiry balloon) reads as planned rather than lost.

## Could not verify

- Whether Inno Setup's [UninstallRun] entry (LANFax.iss:59) executes while {app}\install\Uninstall-LANFaxPrinter.ps1 still exists. If [UninstallRun] runs after file deletion, the printer is never removed on uninstall. ISCC/Inno's docs live outside the granted directories (the handoff notes Inno at E:\Program Files (x86)\Inno Setup 6), and the repo's only check (LogicTests.InstallerScriptTests.Script_compiles_with_inno_setup_when_installed) proves compilation, not execution order.
- Whether {commonappdata} is a valid Inno constant on this Inno 6 version, and whether ISCC validates constants inside [Code] string literals at compile time (LANFax.iss:33-35, :64-65). If it were not expanded, Add-PrinterPort would be handed the literal '{commonappdata}\LANFax\spool\print.pdf' and no fax would ever be picked up; the compile test would only catch it in the [Dirs]/[Files] entries, not the ExpandConstant argument.
- Whether the solution currently builds and all tests pass: I did not run dotnet build/test because publishing/obj writes would change state. During the review several client files were being edited concurrently (EventStream.cs and TrayContext.cs gained resync handling between two of my reads, and my first unbounded reads of LANFax.App sources returned stale content), so the tree may not be in a compiling state at any single point I observed.
- Whether the Microsoft Print To PDF driver actually writes a file-path Local Port silently on this machine class — the spec itself flags this as unverified (client-spec.md 'the silent write-to-path behaviour is unverified and is the first thing phase 2 must prove'); the probe result was never recorded in the spec, and running it requires elevation.
- Exact .NET 10 behaviour of `new UriBuilder(Uri.UriSchemeHttp, "host:port", port).Uri` and of an out-of-range port (whether it throws or yields a wrong endpoint). Finding 1 is written to hold either way — a throw is misclassified as uncertain, and a silently wrong endpoint sends jobs to an unintended host — but the precise exception/message was not confirmed.
- Runtime ACL effects: whether `Get-Acl`/`Set-Acl` in Grant-UsersModify (Install-LANFaxPrinter.ps1:36-41) preserves inherited ACEs on an existing %ProgramData%\LANFax, and whether Inno's `Permissions: users-modify` on {commonappdata}\LANFax propagates to spool\jobs when the [Dirs] entries and the script both run.
